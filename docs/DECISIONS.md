| # | Decision | Why |

| 33 | First schema: `contacts`, `chats`, `messages`, `reactions`. **Identity:** a person or bot is one `contacts` row with a surrogate id and separate typed, device-less columns `lid`, `pn` and `bot` (each unique). The gateway always goes through `contact_id_for(lid, pn, bot)`, which creates the row, fills in a newly learned address, or merges two rows once whatsmeow links a LID and a phone number. The merge folds their direct chats, messages and reactions into one and drops duplicates. The LID is the account and the phone number can move, as in whatsmeow's own LID map: a number seen with a new LID leaves its previous account (recycled number), and a known LID seen with a new number takes it (changed number). Two different LIDs or bots are never merged. When the merge collapses copies of one message it keeps any revoke, the latest edit and a reply link from either copy. The gateway passes the LID whenever whatsmeow knows it, since a phone number on its own can still point at its previous owner. A direct chat is keyed by its contact; groups, broadcast lists and channels by their JID, with a pattern checked per kind. Messages reference chat and sender ids and are unique by `(chat_id, wa_id, sender_id)`, so the LID, phone-number and device spellings of one message are one row. **Edits and revokes** update the row they target (`body`, `edited_at`, `deleted_at`) and are never rows of their own; if the target isn't stored yet, the gateway logs and drops the change. **Reactions** keep the current reaction per sender and message, with no foreign key to messages, since a reaction can arrive before its target; removing a reaction deletes the row. Indexes are added with the query that needs them. Media columns come in phase 1.4. | whatsmeow addresses the same person as a LID, a phone-number JID or a device JID, depending on addressing mode and direction. Keying by raw JID text would split one person, chat or message into several rows, and fixing that after 1.2 and 1.3 have written data would need a data migration. |

It never touches the live database. | Constraints are part of the contract between gateway and core, so they get tested like code, without risking DJ's stored chats or blocking ingest with locks |

| 44 | Gateway ↔ core transport: one outbox table per direction in the shared Postgres. The payload is `jsonb`, written in the same transaction as the data it describes, with `NOTIFY` as a wake-up. Sends go `pending → sending → sent | failed` with the WhatsApp id generated and committed before the network call, and a row left in `sending` is never resent; it reports `outcome_unknown`. Answers the phase 1.0 open question. | Survives either side restarting without losing events, needs no new service (NATS would add a container and its own persistence), and webhooks would still need a durable retry queue on the sending side. | 45 | Contracts are JSON Schema 2020-12 under `contracts/schemas/v1/`, with every payload carrying `"version": 1` and a UUID `id`. | 46 | Events are thin: `message.stored` carries row ids (message, chat, sender) and metadata, never the message body. | 47 | Go types are hand-written and every valid sample must round-trip through them unchanged; every time field is `contracts.Time`, which always encodes as UTC. | 48 | `contracts/` is both a Go module (embedding the schemas) and an npm workspace package (`@kaya/contracts`); the samples are a separate Go package that only tests import. | 49 | Pairing is a one-off `gateway pair` command run by `make pair`, not part of the running service. The connection state sits under `info` in `/health`, uses the contract's connection states and never fails health. whatsmeow keeps its session in its own `whatsmeow_*` tables in the shared database, created on first use through the gateway's existing pool, so the gateway starts even while Postgres is down. whatsmeow reconnects by itself after ordinary drops; the gateway starts a new connection, with backoff, when the first attempt fails or whatsmeow gives up (a refused connection or a temporary ban, waiting out the ban), and stops trying after a logout, a session opened elsewhere or an outdated client. whatsmeow's debug logs are dropped, and JIDs and raw protocol messages in its other lines are masked. The device is named "Kaya". | 51 | Live ingest acknowledges a message to WhatsApp only after it is stored (whatsmeow `SynchronousAck`, its decrypted event buffer, and a handler that reports success). One transaction writes contact, chat, message and the outbox event. A database outage means 30 s of retries, then a dropped connection and redelivery after reconnect. A message that can never be stored is copied to `ingest_dead` (gateway-only, kept until cleared) and then acknowledged. The pairing run holds messages unacknowledged for the gateway. | WhatsApp delivers a live message once. | 52 | Each service has its own Postgres role from phase 1.2 on (brings the role part of #44 forward from 1.6): `kaya_gateway` and `kaya_core`, created `NOLOGIN` by a migration with explicit grants, given passwords from `.env` (`GATEWAY_DB_PASSWORD`, `CORE_DB_PASSWORD`) by a one-shot `db-roles` Compose step. whatsmeow's tables live in a `whatsmeow` schema owned by the gateway role. | 53 | What live ingest stores: text, image, video, audio, voice, document, sticker, location (place name and address only), contact card (display name only) and poll (the question); anything else visible as kind `other` with no text. | 54 | Names: group names come from one all-groups query when the gateway first connects (at most every 12 h), one batched query shortly after a message from an unknown group, and WhatsApp's own change events; never a query per group. `chats.name_set_at` makes sure only a newer name replaces a name. | 55 | History sync is a durable queue. whatsmeow's automatic download is off (`ManualHistorySyncDownload`, `DisableManualHistorySyncReceipt`). Each announced chunk becomes a row in gateway-only `history_jobs`, stored in the transaction that acknowledges the announcement. One worker downloads a chunk, stores it in batches of at most 200 messages with a savepoint per message, marks the job `stored`, clears the announcement (it holds the key to the chunk), and only then confirms the chunk to WhatsApp. A crash repeats the chunk, which changes nothing the second time. A message that cannot be stored becomes a dead letter and the rest go in. A chunk gone from WhatsApp's servers, one that will not decode after 5 tries, or one that waited 7 days is given up on; linking again is the recovery. Only what WhatsApp sends is stored: no on-demand requests, no Status history. | whatsmeow's default path confirms a chunk whether or not anything stored it, so a crash or a database outage during the first sync would lose history for good. | 56 | History emits one `history.synced` event per chunk and no `message.stored` events. A live copy of a message that history stored first turns the row `live` and emits `new`. Names in history only fill a missing name. A live edit or revoke whose message is not stored yet is parked in gateway-only `pending_changes`, applied after each history job, and dropped after 7 days. LID-to-number mappings in a chunk are applied before its messages. | Tens of thousands of per-message events would queue ahead of live commands, and old self-chat messages must never run as commands; phase 3.2 backfills embeddings by scanning rows. Without the flip, a command sent during the first sync could be lost; without parking, a message deleted for everyone during the first sync would later be stored with its text. History addresses a person one way only, so the mappings stop one person becoming two contacts. |
| 57 | Media metadata and keys are separate. `media` (core can read) has one row per image, video, audio, voice or document message: type, size, name, duration, dimensions, the file's own SHA-256 and a state (`remote`, `stored`, `expired`, `failed`). `media_keys` (gateway only) holds what it takes to fetch and decrypt the file. | 58 | Media is downloaded only on request, by the gateway, to files. Files go to `media/<first two hex characters>/<sha256>` under the gateway's data folder, written to `media/tmp` first and renamed, mode 0640. Limits: `MEDIA_MAX_BYTES` (100 MB), checked on the declared size and again while downloading, and no downloads with under 2 GB free. Outcomes: 404 or 410 from WhatsApp is `expired` for good; anything else that fails is `failed` with a code and can be asked for again. A grant core can't use yet would only be attack surface. |
| 59 | Hardening after a review of phases 1.2 to 1.4 (2026-11-22). Only a failure of the database connection counts as an outage; any other error storing a message, including one raised before the query is sent, makes it a dead letter at once, and if even the dead letter is refused the message is acknowledged with its ids kept in hex. Numbers a sender chooses (dimensions, durations, edit and reaction times) are bounded before they reach the database. A panic in the handler is never treated as success. A history job that fails is skipped for a growing while (1 min doubling to 30) so the jobs behind it run; a chunk the database refuses is counted and given up on after 5 tries. The pairing run queues history announcements itself instead of leaving them for the gateway. History reactions are stored, a number spelled `@c.us` is the same number, and a direct chat in history is linked to both of its addresses. Contact rows from whatsmeow are joined per person before names are written. The download size cap is enforced on every write path, download addresses are masked in logs, and a file whose message was deleted while it downloaded is removed. Parked edits and revokes are applied when their message arrives live and purged on connect. | One crafted message (an image claiming an impossible width) was treated as a database outage: never acknowledged, redelivered for ever, and nothing after it stored. whatsmeow confirms a history announcement to WhatsApp before any handler runs, so whether an unstored announcement is sent again is not something the code can rely on (to be checked on a test pairing). A stuck chunk would have blocked the rest until all of them expired together. The size cap was skipped because `io.Copy` uses the file's own `ReadFrom`. A LID row without names was wiping saved names. |

| 61 | Connection health (2026-11-22). The gateway writes a `connection.state` event each time the state or its reason changes, and at no other time. Changes are queued in memory with the time they happened and written in order by one worker; while the database is away the worker keeps trying, keeps at most the newest 64 changes, and reuses each event's id so a write that did go through is never stored twice. Before the gateway stops it writes the state it is stopping in, with three seconds to do so. A retry keeps reporting why the last attempt failed until it connects, so `connecting` appears only at start. Unanswered pings mark the connection `disconnected` with its own reason until WhatsApp answers again, and the connection is replaced after one minute of silence where whatsmeow's default is three. The wait before a new connection doubles after each failure up to a minute and starts over only after a connection has held for a minute in one stretch. A state change is checked and made under one lock, events from a client that was replaced or shut down are ignored, and a watch corrects a state still reported as dropped or silent two minutes after the client is in fact connected. `/health` also says since when the connection has been in its state. `pairing` stays in the contract but is never emitted. | Core, and later `/status` and the alerts, need to know when Kaya cannot see or send messages without polling `/health`. One event per real change keeps a long outage from filling the queue, and the time of the change is what matters to a reader, not the time it was written. A connection that looks open but is dead is the usual result of a sleeping laptop or a router restart; three minutes of a deaf Kaya that reports itself healthy is too long, and replacing a connection is cheap because nothing is acknowledged before it is stored. | 64 | The command channel (2026-11-23). | 65 | Built-in commands and the pause (2026-11-24). ## Open questions

- **Embeddings:** Groq has no embedding model. Options: a small local embedding model (Ollama
  `nomic-embed-text`, or one run inside the Node process) or a hosted embeddings API. Needed by
  phase 3.2.
- **Voice notes:** Groq hosts `whisper-large-v3-turbo`, which could replace the local Whisper service
  in stage 5.
- **Prompt-injection guard:** Groq hosts `meta-llama/llama-prompt-guard-2-86m`, a candidate for
  phase 4.7.

- **Spare SIM for Kaya?** Decides when option B is possible. Asked on 2026-11-20, not answered.
- **Agent framework:** Claude Agent SDK, or a plain Anthropic SDK tool loop with our own router in
  front. The local-first router makes the plain loop the likelier fit; decide at the start of Phase 1.
- **Exact local model (once a local model is added back):** Qwen3 4B, Gemma 3 4B or newer. Pick by
  what's current and what fits in ~3.5 GB VRAM.
- **Telephony provider:** Exotel vs Plivo vs Twilio, depending on whether DJ can get an Indian virtual
  number as an individual (KYC).
- **Fallback alert channel:** Telegram bot or email.
- **Backup target:** Drive or Backblaze B2.
