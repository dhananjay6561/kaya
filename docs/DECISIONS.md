| 33 | First schema: `contacts`, `chats`, `messages`, `reactions`. **Identity:** a person or bot is one `contacts` row with a surrogate id and separate typed, device-less columns `lid`, `pn` and `bot` (each unique). The gateway always goes through `contact_id_for(lid, pn, bot)`, which creates the row, fills in a newly learned address, or merges two rows once whatsmeow links a LID and a phone number. The merge folds their direct chats, messages and reactions into one and drops duplicates. The LID is the account and the phone number can move, as in whatsmeow's own LID map: a number seen with a new LID leaves its previous account (recycled number), and a known LID seen with a new number takes it (changed number). Two different LIDs or bots are never merged. When the merge collapses copies of one message it keeps any revoke, the latest edit and a reply link from either copy. The gateway passes the LID whenever whatsmeow knows it, since a phone number on its own can still point at its previous owner. A direct chat is keyed by its contact; groups, broadcast lists and channels by their JID, with a pattern checked per kind. Messages reference chat and sender ids and are unique by `(chat_id, wa_id, sender_id)`, so the LID, phone-number and device spellings of one message are one row. **Edits and revokes** update the row they target (`body`, `edited_at`, `deleted_at`) and are never rows of their own; if the target isn't stored yet, the gateway logs and drops the change. **Reactions** keep the current reaction per sender and message, with no foreign key to messages, since a reaction can arrive before its target; removing a reaction deletes the row. Indexes are added with the query that needs them. Media columns come in phase 1.4. | whatsmeow addresses the same person as a LID, a phone-number JID or a device JID, depending on addressing mode and direction. Keying by raw JID text would split one person, chat or message into several rows, and fixing that after 1.2 and 1.3 have written data would need a data migration. |

| 44 | Gateway ↔ core transport: one outbox table per direction in the shared Postgres. The payload is `jsonb`, written in the same transaction as the data it describes, with `NOTIFY` as a wake-up. | 48 | `contracts/` is both a Go module (embedding the schemas) and an npm workspace package (`@kaya/contracts`); the samples are a separate Go package that only tests import. | 54 | Names: group names come from one all-groups query when the gateway first connects (at most every 12 h), one batched query shortly after a message from an unknown group, and WhatsApp's own change events; never a query per group. `chats.name_set_at` makes sure only a newer name replaces a name. | 55 | History sync is a durable queue. whatsmeow's automatic download is off (`ManualHistorySyncDownload`, `DisableManualHistorySyncReceipt`). Each announced chunk becomes a row in gateway-only `history_jobs`, stored in the transaction that acknowledges the announcement. One worker downloads a chunk, stores it in batches of at most 200 messages with a savepoint per message, marks the job `stored`, clears the announcement (it holds the key to the chunk), and only then confirms the chunk to WhatsApp. A crash repeats the chunk, which changes nothing the second time. A message that cannot be stored becomes a dead letter and the rest go in. A chunk gone from WhatsApp's servers, one that will not decode after 5 tries, or one that waited 7 days is given up on; linking again is the recovery. Only what WhatsApp sends is stored: no on-demand requests, no Status history. | whatsmeow's default path confirms a chunk whether or not anything stored it, so a crash or a database outage during the first sync would lose history for good. | 56 | History emits one `history.synced` event per chunk and no `message.stored` events. A live copy of a message that history stored first turns the row `live` and emits `new`. LID-to-number mappings in a chunk are applied before its messages. | Tens of thousands of per-message events would queue ahead of live commands, and old self-chat messages must never run as commands; phase 3.2 backfills embeddings by scanning rows. | 58 | Media is downloaded only on request, by the gateway, to files. | 59 | Hardening after a review of phases 1.2 to 1.4 (2026-11-22). The pairing run queues history announcements itself instead of leaving them for the gateway. History reactions are stored, a number spelled `@c.us` is the same number, and a direct chat in history is linked to both of its addresses. Contact rows from whatsmeow are joined per person before names are written. The download size cap is enforced on every write path, download addresses are masked in logs, and a file whose message was deleted while it downloaded is removed. Parked edits and revokes are applied when their message arrives live and purged on connect. | One crafted message (an image claiming an impossible width) was treated as a database outage: never acknowledged, redelivered for ever, and nothing after it stored. whatsmeow confirms a history announcement to WhatsApp before any handler runs, so whether an unstored announcement is sent again is not something the code can rely on (to be checked on a test pairing). | 61 | Connection health (2026-11-22). The gateway writes a `connection.state` event each time the state or its reason changes, and at no other time. Changes are queued in memory with the time they happened and written in order by one worker; while the database is away the worker keeps trying, keeps at most the newest 64 changes, and reuses each event's id so a write that did go through is never stored twice. Before the gateway stops it writes the state it is stopping in, with three seconds to do so. A retry keeps reporting why the last attempt failed until it connects, so `connecting` appears only at start. Unanswered pings mark the connection `disconnected` with its own reason until WhatsApp answers again, and the connection is replaced after one minute of silence where whatsmeow's default is three. The wait before a new connection doubles after each failure up to a minute and starts over only after a connection has held for a minute in one stretch. A state change is checked and made under one lock, events from a client that was replaced or shut down are ignored, and a watch corrects a state still reported as dropped or silent two minutes after the client is in fact connected. `/health` also says since when the connection has been in its state. `pairing` stays in the contract but is never emitted. | Core, and later `/status` and the alerts, need to know when Kaya cannot see or send messages without polling `/health`.
