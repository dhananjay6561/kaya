## Settled (2026-11-20)

| # | Decision | Why |
|---|---|---|
| 1 | Build our own agent instead of running OpenClaw | Full control over what it can touch, since it reads chats and can spend money. OpenClaw has had security problems with exposed instances and untrusted community skills. |
| 2 | Host on DJ's Victus (Linux Mint), Docker Compose | DJ owns it outright, and it's dedicated to this |
| 3 | ~~Agent hub in Node/TypeScript, including WhatsApp~~ Superseded by #23 | Baileys (the WhatsApp library) is Node |
| 4 | WhatsApp as a linked device on DJ's number (QR or pairing code) | The official Business API can't read personal chats. This is also how the real IRA did it: DJ scanned a QR. |
| 5 | Hybrid models: local ~4B on Ollama is the gatekeeper, Claude API for multi-step work | 4 GB VRAM can't run a model good enough for long tool chains; local keeps raw chats on the laptop and cuts cost |
| 6 | Privacy = fixed masking rules + local model picking relevant messages | A 4B model alone misses things; fixed rules are predictable |
| 7 | Postgres + pgvector (supersedes "SQLite to start") | Several services share data, and pgvector gives meaning-based chat search |
| 8 | Whisper on the CPU | Leaves the GPU free for the LLM |
| 9 | Calls always use cloud STT + Claude + ElevenLabs | Live calls need sub-second replies; the local model is too slow |
| 10 | Kaya identifies as an AI on calls, never as DJ | Passing as a human deceives the person called |
| 11 | Confirm before any outward action (messages, payments, calls) | It has access to DJ's accounts and money |
| 12 | Tailscale is the only way in; Cloudflare Tunnel only for `/voice/*` | No open ports on a box holding all of DJ's sessions |
| 13 | Browser logins: DJ logs in once via noVNC, no stored passwords | Passwords never live on disk |
| 14 | Start talking to Kaya in the self-chat (option A); spare SIM (B) later | Zero setup to start; B makes Kaya a real contact once it works |

## Settled (2026-11-22)

| # | Decision | Why |
|---|---|---|
| 28 | Containers: core on `distroless/nodejs24`, gateway on `distroless/static`, both as the non-root user with a read-only root filesystem and no capabilities. Postgres is `pgvector/pgvector` on Postgres 18. Every base image is pinned by version and digest, and Dependabot updates them. The distroless Node image has no version tag, so the core build fails unless its Node matches the build stage (v24.22.3). Build stages use Debian (`node:*-trixie-slim`) so native packages are built for the same libc (glibc) as the runtime. | Small images with no shell or package manager to exploit; digests make builds repeatable |
| 29 | Each service has a minimal `/health` from phase 0.5 so Compose health checks work; phase 0.7 adds db status. A `healthcheck` command inside each image calls it, since distroless images have no curl. | `docker compose up` can only report healthy if the services run and answer |
| 30 | Services bind to `127.0.0.1` by default (`LISTEN_HOST`); Compose binds `0.0.0.0` inside containers and publishes ports on `127.0.0.1` only | Nothing is reachable from the network unless Tailscale or the tunnel is set up for it |
| 31 | The gateway container gets only the settings it uses, not the whole `.env` | The service holding the WhatsApp session never sees API keys |
| 32 | Migrations run in a one-shot `migrate` Compose service (dbmate, as a non-root user, read-only, in strict mode so an out-of-order migration fails); core and gateway start only after it succeeds. No `schema.sql` dump is committed. `make rollback` asks before touching the live database. | Services never start against an old schema, and neither language runs migrations itself (#25). The migration files are the schema's single source. Stacked phase branches can produce out-of-order timestamps, which strict mode catches. |
| 33 | First schema: `contacts`, `chats`, `messages`, `reactions`. **Identity:** a person or bot is one `contacts` row with a surrogate id and separate typed, device-less columns `lid`, `pn` and `bot` (each unique). The gateway always goes through `contact_id_for(lid, pn, bot)`, which creates the row, fills in a newly learned address, or merges two rows once whatsmeow links a LID and a phone number. The merge folds their direct chats, messages and reactions into one and drops duplicates. The LID is the account and the phone number can move, as in whatsmeow's own LID map: a number seen with a new LID leaves its previous account (recycled number), and a known LID seen with a new number takes it (changed number). Two different LIDs or bots are never merged. When the merge collapses copies of one message it keeps any revoke, the latest edit and a reply link from either copy. The gateway passes the LID whenever whatsmeow knows it, since a phone number on its own can still point at its previous owner. A direct chat is keyed by its contact; groups, broadcast lists and channels by their JID, with a pattern checked per kind. Messages reference chat and sender ids and are unique by `(chat_id, wa_id, sender_id)`, so the LID, phone-number and device spellings of one message are one row. **Edits and revokes** update the row they target (`body`, `edited_at`, `deleted_at`) and are never rows of their own; if the target isn't stored yet, the gateway logs and drops the change. **Reactions** keep the current reaction per sender and message, with no foreign key to messages, since a reaction can arrive before its target; removing a reaction deletes the row. Indexes are added with the query that needs them. Media columns come in phase 1.4. | whatsmeow addresses the same person as a LID, a phone-number JID or a device JID, depending on addressing mode and direction. Keying by raw JID text would split one person, chat or message into several rows, and fixing that after 1.2 and 1.3 have written data would need a data migration. |
| 34 | Schema tests are plain SQL in `db/tests/`. `make test-db` runs them on a throwaway `kaya_schema_test` database: migrate, rerun (must apply nothing), roll back, reapply, then the tests, and it drops the database afterwards. CI runs the same target. It never touches the live database. | Constraints are part of the contract between gateway and core, so they get tested like code, without risking DJ's stored chats or blocking ingest with locks |
| 35 | Logging with pino in core and `log/slog` in the gateway, both writing JSON to stdout with the same core fields and lowercase level names. Errors go under one `err` key with at least `type` and `message` in both (`logging.Err` in Go). Request ids travel in `X-Request-Id`. `/health` requests log at debug even when they fail, since the failing check already logs a warning. | Standard, fast libraries; one log shape makes it possible to follow a request across services and query failures the same way, and error-level lines stay meaningful for alerting |
| 36 | `/health` checks the db on every call (2 s limit) and answers 503 when it's down. Services don't exit when the db is unreachable; they start and report it. The response never includes error details. A timed-out check destroys its pooled connection instead of leaving it checked out. For now `/health` serves as both liveness and readiness, which is fine under plain Compose (it doesn't restart unhealthy containers); split it before adding autoheal or a `service_healthy` dependency between core and gateway, so a db blip can't cascade. Typed errors at HTTP boundaries arrive with the first real route (1.6); until then the only routes are `/health` and the panic and 500 handlers. | Docker and later monitoring see a real readiness signal, a db restart doesn't crash-loop the services, and the endpoint can't leak internals |
| 37 | Core logs errors through an allowlist serialiser (type, message, stack, code and a few more, plus the cause chain) | `pg` attaches its whole client to errors; logging that is noisy and a leak risk |
| 38 | Database tests run when `TEST_DATABASE_URL` is set; CI starts a pgvector Postgres for the core and gateway jobs | Real-Postgres tests (ARCHITECTURE) without making every local test run need Docker |
| 39 | Providers in core follow one pattern: interface, one file per implementation, an exhaustive factory switch on a config enum that lists only built implementations, and a `stub` for each kind | Swapping is a config change, and the type checker catches a provider that is configurable but not wired |
| 40 | `LLM_PROVIDER` is `groq` or `stub` (default groq, unchanged). `GROQ_API_KEY` is required only for groq. Until phase 3.1 the groq provider exists but its calls reject with `ProviderNotReadyError`, so the default config keeps working. | Keeps decision #17 as the default while letting development and tests run with no key |
| 41 | `CHAT_CHANNEL` and `TELEPHONY_PROVIDER` start with `stub` only; the gateway channel arrives in 1.6 and phone calls in stage 13. The PR that adds a real implementation also makes it the default (or makes the key required), so an old `.env` can't silently keep a stub. Core logs a warning at startup for every stub in use. Stubs never report that an outward action happened: the telephony stub answers `failed` with no transcript unless a test scripts an outcome. In stage 13 the vendor (Exotel, Plivo or Twilio) sits inside `services/voice`, so core's real telephony provider will be a client of that service, named `voice`, not after the vendor. | No placeholder for a provider whose transport isn't decided yet (1.0, 13.1), and no way for a forgotten default or a stub to tell DJ that a message went out or a call happened |
| 42 | The chat channel is only the DJ ↔ Kaya conversation. Reading other chats goes through the database the gateway fills. | Keeps safety rule 3 (Kaya talks in one place) in the shape of the interface |
| 43 | Outward actions are idempotent at the interface: `CallRequest` and `OutgoingMessage` carry a required `idempotencyKey` (the confirmed pending-action id from 4.6, or a fresh id for Kaya's own replies), and a repeated key returns the earlier result instead of acting again. `Completion` has a `finishReason`, so a reply cut off at `maxTokens` is never sent as if complete. | A timeout followed by a retry must not call Rahul twice (ARCHITECTURE: a retry never duplicates work) |
| 44 | Gateway ↔ core transport: one outbox table per direction in the shared Postgres. The payload is `jsonb`, written in the same transaction as the data it describes, with `NOTIFY` as a wake-up. There is exactly one consumer per table, which drains in `seq` order on start. Delivery is at least once: the handled id commits with the handler's effects. Sends go `pending → sending → sent | failed` with the WhatsApp id generated and committed before the network call, and a row left in `sending` is never resent; it reports `outcome_unknown`. Poison rows go to `dead`, handled rows are deleted after 7 days, and each service gets its own Postgres role that can't write the other's queue. Details in ARCHITECTURE "How services talk". Answers the phase 1.0 open question. | Survives either side restarting without losing events, needs no new service (NATS would add a container and its own persistence), and webhooks would still need a durable retry queue on the sending side. Spelling out the semantics now keeps 1.2 and 1.6 from building on "idempotent because there's a UUID", which isn't true for sends. |
| 45 | Contracts are JSON Schema 2020-12 under `contracts/schemas/v1/`, with every payload carrying `"version": 1` and a UUID `id`. Formats are pinned with patterns (lowercase UUIDs; UTC timestamps with uppercase `T` and `Z`; text needing a character other than an ASCII space, tab or line break), so ajv and the Go validator can't disagree. Compatible changes stay in v1; breaking ones get a new version folder. | One language-neutral source (#27); versions make breaking changes explicit; the two validators' `format` implementations differ (ajv accepts `urn:uuid:` and lowercase `t`), and patterns remove that gap |
| 46 | Events are thin: `message.stored` carries row ids (message, chat, sender) and metadata, never the message body. The gateway emits it only when the upsert inserted or changed the row, and core keys command handling on `(message_id, change)`, so a redelivered or overlapping copy of one WhatsApp message can't run a command twice. | Chat text lives in one place (the database), so the queue and logs never hold private content; ids match the identity model (#33), so a JID's spelling never reaches core |
| 47 | Go types are hand-written and every valid sample must round-trip through them unchanged; every time field is `contracts.Time`, which always encodes as UTC. TypeScript types are generated from the schemas (`make contracts`), and a test fails if they are stale. ajv (with ajv-formats) and santhosh-tekuri/jsonschema validate at runtime. Go validation errors report only field locations and rule names, never values. | Generated Go from JSON Schema is awkward to use, and the round-trip test catches drift instead. whatsmeow returns local times, and santhosh-tekuri's messages embed the rejected value (phone numbers, message text), which must not reach logs (#46). |
| 48 | `contracts/` is both a Go module (embedding the schemas) and an npm workspace package (`@kaya/contracts`); the samples are a separate Go package that only tests import. Both images build from the repo root, with a `Dockerfile.dockerignore` per service. Send requests carry an `authorization` (`self_chat`, or `confirmed` with the pending action's id) and an `expires_at`, and may only target people and groups. | Both services read the same files at build and run time with no copying step that could drift, and invalid payloads never ship in a binary. Confirm-before-act and expiry need fields the gateway can check, because the contract is the last gate before the WhatsApp socket and posting to Status or a channel would reach everyone. |
| 49 | Pairing is a one-off `gateway pair` command run by `make pair`, not part of the running service. It stops the gateway, links a new device by a QR code drawn in the terminal or by a pairing code (`PHONE=`), and starts the gateway again. The running gateway connects only when a session is stored; until then `/health` reports WhatsApp as `logged_out`, "not paired". The connection state sits under `info` in `/health`, uses the contract's connection states and never fails health. whatsmeow keeps its session in its own `whatsmeow_*` tables in the shared database, created on first use through the gateway's existing pool, so the gateway starts even while Postgres is down. whatsmeow reconnects by itself after ordinary drops; the gateway starts a new connection, with backoff, when the first attempt fails or whatsmeow gives up (a refused connection or a temporary ban, waiting out the ban), and stops trying after a logout, a session opened elsewhere or an outdated client. whatsmeow's debug logs are dropped, and JIDs and raw protocol messages in its other lines are masked. The device is named "Kaya". QR codes are drawn with `rsc.io/qr` directly. | Pairing needs a person at a terminal and happens once; keeping it out of the service keeps the service non-interactive, and stopping the gateway first means two clients never share one session. CI and a fresh install have no phone, so an unpaired gateway has to stay healthy. whatsmeow's debug logs can contain message contents, and its warnings name senders by phone number. The usual terminal QR library ships a stray build artifact and three more dependencies for what is 30 lines on top of its encoder. |
| 50 | DJ's number is paired to check phases 1.1 to 1.3 and unlinked each time; it is linked for good after phase 1.4 (changed 2026-11-22 from "after 1.3"). | WhatsApp sends the chat history once, right after a device links, and nothing stores it before 1.3. The keys for old media arrive only inside that history, and a stored message is never overwritten, so linking for good before 1.4 would leave every old photo and voice note impossible to fetch. Linking again triggers a fresh history sync. |
| 51 | Live ingest acknowledges a message to WhatsApp only after it is stored (whatsmeow `SynchronousAck`, its decrypted event buffer, and a handler that reports success). One transaction writes contact, chat, message and the outbox event. A database outage means 30 s of retries, then a dropped connection and redelivery after reconnect. A message that can never be stored is copied to `ingest_dead` (gateway-only, kept until cleared) and then acknowledged. The pairing run holds messages unacknowledged for the gateway. | WhatsApp delivers a live message once. Without the event buffer, an outage of the session store makes whatsmeow acknowledge messages it could not decrypt. A log line can't bring a message back; a dead-letter row can be replayed. |
| 52 | Each service has its own Postgres role from phase 1.2 on (brings the role part of #44 forward from 1.6): `kaya_gateway` and `kaya_core`, created `NOLOGIN` by a migration with explicit grants, given passwords from `.env` (`GATEWAY_DB_PASSWORD`, `CORE_DB_PASSWORD`) by a one-shot `db-roles` Compose step. whatsmeow's tables live in a `whatsmeow` schema owned by the gateway role. Core no longer receives the whole `.env`, so it never sees the admin password. Services read `GATEWAY_DATABASE_URL` / `CORE_DATABASE_URL` and fall back to `DATABASE_URL`. | Core is the part exposed to prompt injection, and whatsmeow's tables hold the encryption keys and, briefly, message plaintext. Moving those tables is free only while the phone is unlinked (#50). Passwords stay out of migrations because the repo is public. |
| 53 | What live ingest stores: text, image, video, audio, voice, document, sticker, location (place name and address only), contact card (display name only) and poll (the question); anything else visible as kind `other` with no text. Edits, delete-for-everyone and reactions are applied as they arrive; an edit or revoke only reaches the sender's own message, except a group admin's revoke. Skipped: Status, channels, poll votes, pins and protocol housekeeping. View-once messages get a row with no content (`messages.view_once`). Disappearing messages are stored with their expiry (`messages.expires_at`) and kept. "Delete for me" is ignored. Defaults for DJ to review are marked in `DECISIONS-FOR-REVIEW.md`. | Q&A over chats needs who, where, when and the current text, and must not answer from edited or deleted text. Storing unknown types as `other` means a new WhatsApp message type is never silently dropped. Other people's numbers and coordinates aren't needed to answer questions. |
| 54 | Names: group names come from one all-groups query when the gateway first connects (at most every 12 h), one batched query shortly after a message from an unknown group, and WhatsApp's own change events; never a query per group. `chats.name_set_at` makes sure only a newer name replaces a name. A person's own name and business name are saved as their messages arrive; address-book names are copied from whatsmeow's contact store on connect and after its contact sync, which asks nothing of WhatsApp. | Fewer requests to WhatsApp means lower ban risk. A message never waits for a name. |
| 55 | History sync is a durable queue. whatsmeow's automatic download is off (`ManualHistorySyncDownload`, `DisableManualHistorySyncReceipt`). Each announced chunk becomes a row in gateway-only `history_jobs`, stored in the transaction that acknowledges the announcement. One worker downloads a chunk, stores it in batches of at most 200 messages with a savepoint per message, marks the job `stored`, clears the announcement (it holds the key to the chunk), and only then confirms the chunk to WhatsApp. A crash repeats the chunk, which changes nothing the second time. A message that cannot be stored becomes a dead letter and the rest go in. A chunk gone from WhatsApp's servers, one that will not decode after 5 tries, or one that waited 7 days is given up on; linking again is the recovery. Only what WhatsApp sends is stored: no on-demand requests, no Status history. | whatsmeow's default path confirms a chunk whether or not anything stored it, so a crash or a database outage during the first sync would lose history for good. Small batches keep live messages from waiting behind history, since resolving contacts takes a lock until commit. Extra requests to the phone are ban risk. |
| 56 | History emits one `history.synced` event per chunk and no `message.stored` events. A live copy of a message that history stored first turns the row `live` and emits `new`. Names in history only fill a missing name. A live edit or revoke whose message is not stored yet is parked in gateway-only `pending_changes`, applied after each history job, and dropped after 7 days. LID-to-number mappings in a chunk are applied before its messages. | Tens of thousands of per-message events would queue ahead of live commands, and old self-chat messages must never run as commands; phase 3.2 backfills embeddings by scanning rows. Without the flip, a command sent during the first sync could be lost; without parking, a message deleted for everyone during the first sync would later be stored with its text. History addresses a person one way only, so the mappings stop one person becoming two contacts. |

## Open questions

- **Embeddings:** Groq has no embedding model. Options: a small local embedding model (Ollama
  `nomic-embed-text`, or one run inside the Node process) or a hosted embeddings API. Needed by
  phase 3.2.
- **Voice notes:** Groq hosts `whisper-large-v3-turbo`, which could replace the local Whisper service
  in stage 5.
- **Prompt-injection guard:** Groq hosts `meta-llama/llama-prompt-guard-2-86m`, a candidate for
  phase 4.7.

- **Spare SIM for Kaya?** Decides when option B is possible. Asked on 2026-11-20, not answered.
- **Agent framework:** Claude Agent SDK, or a plain Anthropic SDK tool loop with our own router in
  front. The local-first router makes the plain loop the likelier fit; decide at the start of Phase 1.
- **Exact local model (once a local model is added back):** Qwen3 4B, Gemma 3 4B or newer. Pick by
  what's current and what fits in ~3.5 GB VRAM.
- **Telephony provider:** Exotel vs Plivo vs Twilio, depending on whether DJ can get an Indian virtual
  number as an individual (KYC).
- **Fallback alert channel:** Telegram bot or email.
- **Backup target:** Drive or Backblaze B2.
